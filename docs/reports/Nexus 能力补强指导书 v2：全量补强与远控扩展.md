## 零、最高原则：单一软件界面（不可违背）

所有交付形态必须是**单一桌面/移动软件**，用户双击（或点击）一个图标即可使用，严禁出现需要手动启动服务、手动打开浏览器、手动配置端口等形态。

- Windows：单一 `.exe`。
- Android：单一 `.apk`。
- 开发阶段允许 dev server 热重载，最终交付物必须是打包好的单一可执行文件。

**具体技术方案（Android 框架、通信协议、远控实现、多开管理）由 AI 在调研后自行决定**，本指导书不定死，但必须满足上述原则。

## 一、补强背景与目标

### 1.1 背景

Nexus 目前是一个 PC 端本地 AI Agent 算力监控中心，已实现 Agent 数据的读取、汇总与展示。用户实际使用中存在以下新需求：

- 需要在移动端（Android）远程查看数据。
- 需要监控 PC 本身的系统状态（帧率、CPU、内存等）。
- 需要对 ZCode 进行远程反向控制。
- ZCode 多开（当前 5 个，未来可能更多），需要统一管理。
- 之前讨论的多个补强项（历史趋势、健康度评分、告警、成本估算、数据导出、搜索筛选、会话详情、赛博账单、健康提醒、拟人化彩蛋、插件市场、AI 洞察引擎等）全部采纳，但需 AI 先调研评估再执行。

### 1.2 补强目标

将 Nexus 从「PC 端单机监控」升级为：

- **双端监控**：PC + Android 跨设备监控。
- **全维度数据**：Agent 数据 + PC 系统状态数据 + 历史趋势 + 健康评分 + 成本估算等。
- **有限反控**：仅对 ZCode 和 DeepSeek Harness 开放反向控制。
- **多开管理**：统一识别和管理多个 ZCode 实例。
- **布局整合**：新增内容较多，需由 AI 重新设计整体布局与信息架构。

### 2.1 任务一：现有 Nexus 代码库调研

**输出**：《Nexus 现状调研报告》《共享层抽象建议》。

### 2.2 任务二：ZCode 开源远控组件调研

用户已将 ZCode 开源源码放在 `F:\ZCode-main`。AI 必须深度分析其中的远控组件，输出《ZCode 远控源码分析报告》，包含：

**输出**：《ZCode 远控源码分析报告》《ZCode 远控复用方案》。

### 2.3 任务三：DeepSeek Harness 开源调研

DeepSeek Harness 是开源且插件化的工具。AI 必须调研其：

- 本地运行方式、进程结构、配置文件格式。

### 2.4 任务四：远程监控与通信方案调研

- 局域网直连、公网 P2P、中继服务器、蓝牙、扫码配对等混合模式可行性。
- NAT 穿透能力、加密方式、延迟表现。

- 与 ZCode 远控组件结合的方式。

**输出**：《通信方案调研报告》《混合通信架构设计草案》。

### 2.5 任务五：Android 端技术选型

对比至少 3 种 Android 端技术方案（Flutter / React Native / 原生 Kotlin / 其他），评估：

- 图表库生态（饼图、折线图、热力图等丰富可视化）。
- 与 PC 端共享层（Go module / Protobuf / JSON Schema）的集成难度。
- 远控功能的实现可行性。

**输出**：《Android 端技术选型建议》。

### 2.6 任务六：多开 ZCode 管理方案调研

## 三、核心补强内容

### 3.1 Android 端应用

Android 端是独立单一 `.apk`，通过混合通信方式连接 PC 端，展示丰富数据看板，并支持有限反控。

**必须实现**：
- 连接 PC 端（多种通信方式可选，混合模式）。
- 展示 Agent 数据看板（Token、会话、工具调用等）。
- 展示 PC 系统状态看板（帧率、CPU、内存、磁盘、网络等，不限于）。
- 支持多开 ZCode 实例的查看与管理。
- 支持对 ZCode 和 DeepSeek Harness 的远程反向控制。
- 界面精美，参考 ZCode 源码设计语言。
- 移动端专门适配。

**不做的事**：
- 不修改 PC 端其他 Agent 的配置或日志。
- 不提供对其他 Agent 的反控（可留占位 UI，但不实现）。
- 不提供任务调度或 Agent 切换功能（远控仅限 ZCode / DeepSeek Harness 的启动/停止/状态查看等）。

### 3.2 双标签页与布局重构

Android 端主界面采用标签页形式。原有「Agent 数据看板」「电脑数据看板」命名需由 AI 重新设计，更贴切、更有产品感。

**基本标签页（AI 可调整命名与数量）**：
- 标签页 A：Agent 数据（含多开 ZCode 管理视图）。
- 标签页 B：PC 系统状态。
- 标签页 C（可选）：由 AI 根据补强项决定（如综合概览、历史趋势、告警中心等）。

**布局重构要求**：
- 新增内容（历史趋势、健康评分、成本估算、搜索筛选、会话详情、赛博账单等）需要合理融入现有布局。
- 由 AI 决定哪些内容放在主标签页、哪些放在二级页面、哪些放在设置中。
- 保持信息密度高、层次清晰、移动端可读性强。

### 3.3 有限反向控制

仅对以下两个目标开放反控：

**ZCode**：
- 直接复用 `F:\ZCode-main` 中的远控组件。
- 支持操作：查看实例状态、启动/停止任务、查看任务输出、切换模型、重启实例等（具体指令集由 AI 调研后决定）。
- 多开支持：需识别本机所有 ZCode 实例，Android 端可选择目标实例进行操作。

**DeepSeek Harness**：
- 利用其开源与插件化特性，集成其远程控制接口。
- 支持操作：查看运行状态、启停任务、获取输出等（由 AI 调研后决定）。

**其他 Agent**：
- 保留占位 UI（如有需要），但不实现反控功能。
- 不修改其他 Agent 的任何配置。

### 3.4 多开 ZCode 管理

- 自动发现本机所有 ZCode 实例。
- 为每个实例独立采集 Token、会话、工具调用数据。
- 在 Android 端提供聚合视图（总消耗）与独立视图（按实例拆分）。
- 远控时精确指定目标实例。
- 具体识别方式（进程名、端口、配置目录、数据库路径）由 AI 调研后决定。

### 3.5 全量补强项（由 AI 评估后执行）

以下项目全部采纳，但执行细节、优先级、实现方式由 AI 根据调研结果自行决定：

- 历史趋势与时间机器
- 异常检测与智能告警
- Agent 健康度评分
- 成本估算与预算追踪
- 多设备同步
- 数据导出与报告生成
- 搜索与筛选
- 会话详情查看
- 年度/月度赛博账单
- 健康提醒
- Agent 拟人化彩蛋
- 插件市场
- AI 洞察引擎

**执行要求**：
- 每项补强必须先输出《评估报告》，说明可行性、依赖、影响范围、建议优先级。
- 经评估后若认为某项不适合当前阶段实现，可记录理由并延后，但不得跳过评估。

## 四、技术架构设计

### 4.1 整体架构

- **PC 端**：采集 Agent 数据 + 系统状态数据；提供远程通信服务；执行有限反控指令；管理多开 ZCode 实例。
- **Android 端**：连接 PC 端；展示数据看板；下发反控指令；管理多开实例视图。
- **共享层**：数据模型、聚合算法、通信协议定义、图表配置等，抽象为两端可复用的库（形式由 AI 决定）。

### 4.2 PC 端模块扩展

在现有 Nexus 基础上新增/扩展：

- **system-collector**：系统状态数据采集。
- **remote-server**：远程通信服务（混合模式）。
- **zcode-manager**：多开 ZCode 实例识别与管理。
- **remote-control**：反控指令处理（仅 ZCode / DeepSeek Harness）。
- **shared**：共享层。

### 4.3 Android 端模块设计

模块化单体结构：

- **connection**：连接管理（混合模式、配对、加密）。
- **agent-data**：Agent 数据展示（含多开视图）。
- **system-data**：PC 系统状态展示。
- **remote-control**：反控操作界面。
- **dashboard**：图表渲染、标签页、下钻交互。
- **settings**：通信方式、采集频率、主题、告警阈值等。

### 4.4 技术选型（由 AI 调研后决定）

- **Android 框架**：Flutter / React Native / 原生 Kotlin / 其他。
- **通信协议**：WebSocket / gRPC / WebRTC / MQTT / 其他，支持混合。
- **图表库**：fl_chart / ECharts / 其他。
- **共享层形式**：Go module / Protobuf / JSON Schema / 其他。
- **ZCode 远控复用方式**：直接引用源码 / 协议适配 / 其他。

## 五、UI/UX 设计规范

### 5.1 设计语言来源

Android 端视觉设计语言直接参考 `F:\ZCode-main` 源码，提取色彩、间距、圆角、字体、动效、组件样式等 Token。

### 5.2 移动端适配

- 标签页切换采用底部导航或顶部 Tab。
- KPI 卡片适配单列或双列。
- 图表高度适配屏幕比例。
- 支持横屏（可选）。
- 支持深色 / 亮色模式。

### 5.3 去 AI 感原则

严禁：紫蓝渐变、渐变标题、超大圆角、装饰性动效、卡片堆砌、表情泛滥、营销词汇、玻璃态外壳。

### 5.4 看板视觉要求

- 数据密度高、色彩克制、层次清晰、可读性强。
- 图表类型丰富：饼图、折线图、热力图、环形图、柱状图、仪表盘、雷达图、桑基图等。
